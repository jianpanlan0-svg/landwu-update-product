# 上传器说明

## 结构

- 本地服务：负责登录态保存、任务执行、队列调度、报告生成。
- 本地网页：负责可视化操作、进度展示、历史任务展示。
- 脚本猫桥接：负责把当前领物网页登录态同步到本地服务。
- 三步脚本：分别处理上传图库、批量设计、TEMU 汇出。

## 三步流程

### 1. 上传图库

- 输入图片文件夹和任务标签；默认任务标签格式为 `YYYYMMDDHHmmss`，精确到秒。
- 批量上传图片到领物图库，并统一设置标签。
- 单张图片失败会自动重试 1 次。
- 重试后仍失败的图片会复制到 `上传失败_标签_店铺_公版` 目录，原图不删除。
- 全部上传成功后，原图片文件夹会自动标记为 `（已上传图库）`。

### 2. 批量设计

- 用标签筛选第一步上传的主题图。
- 用公版名称搜索并精确匹配设计公版。
- 支持“最大化设计”选项，默认不勾选。
- 接口直接生成成品，不依赖网页逐张预览渲染。
- 第二步接口如果返回非 JSON、HTML 错误页或网络异常，会自动重试 1 次；第二次仍失败才写入失败报告。

### 3. TEMU 汇出

- 用标签筛选成品列表。
- 选择店铺和汇出模板。
- 默认 SKC 规则为店铺名提取安全前缀 + 日期，不包含 `TEMU` 和中文。
- 支持多店铺：第一家跑完整流程，后续店铺只跑第三步汇出。
- 第三步接口如果返回非 JSON、HTML 错误页或网络异常，会自动重试 1 次；第二次仍失败才写入失败报告。

## 队列

- 可以立即执行当前任务，也可以加入任务队列。
- 如果任务正在运行，新增队列会在当前任务结束后自动续跑。
- 队列项显示文件夹、标签、执行步骤、公版、店铺，以及状态（待执行 / 运行中 / 已完成 / 失败）。

### 失败重试

- 失败项会显示「重试」按钮，点击后重新排队执行；失败原因显示真实报错，不再只是子进程退出码。
- 若失败项本身包含「上传图库」，重试前会二次确认——重跑会把同一批图片重新上传一遍。
- 顺序保护：多店铺时第一项承载全流程、后续项只有第三步（见「三步流程 §3」）。若第一项仍是失败状态，
  直接重试后面的项会被拦截并提示先重试第一项，因为成品还不存在，第三步只会报
  `未找到标签为 xxx 的成品`。**队列顺序就是依赖顺序，按从上到下的顺序重试。**

## 报告与失败处理

- 每一步都会在 `reports/` 下生成 JSON 报告。
- 第一阶段失败报告包含失败文件、失败原因、复制目标、重试记录。
- 前端历史任务会展示成功、失败、店铺、标签和执行时间。
- 三步流程如果在第二步或第三步失败，会保留前面已完成步骤的真实结果，并在失败步骤显示失败原因，不再只显示子进程退出码。
- `reports/` 是本地运行产物，不提交到 Git。

## 本地配置

- `auth-state-v1.json`：网页登录态，本地生成，不提交。
- `obs-config.json`：OBS 密钥，本地生成，不提交。
- `obs-config.example.json`：OBS 配置示例，可以提交。

## 本地开发

- 改完 `uploader-server-v1.js` 或 `ui/` 下任何文件后，**必须重启本地服务进程**，否则浏览器里跑的还是旧代码。
- 判断服务是否在运行、当前生效哪个版本：

```bash
curl -s http://127.0.0.1:18321/api/status
```

返回里的 `version` 字段就是当前生效版本；`running: true` 表示有任务正在执行，此时重启会打断任务。

- 前端脚本按版本号迭代：复制 `ui/app-vN.js` 为 `ui/app-v(N+1).js` 再改，保留旧文件作历史版本，
  并同步 `ui/index.html` 里的 `<script src>` 引用。

## 常用命令

```bash
npm install
npm start
npm run build:exe
npm run build:mac-package
```

GitHub Actions 自动打包：

- 推送到 `main`：自动构建 Windows EXE 目录和 Mac Apple 芯片 `.app` 压缩包，结果在 Actions 的 Artifacts 下载。
- 推送 `v*` 标签：自动创建 GitHub Release，并上传 Windows / Mac 压缩包。

Release 发布流程：

```bash
git status --short
git tag -a v版本号 -m "Release v版本号"
git push origin v版本号
```

发布验收：

- Actions 页面确认 Windows、Mac、Release 三个任务全部成功。
- Release 页面确认存在对应版本。
- Release Assets 确认存在 Windows EXE 包和 Mac APP 包。
- 没确认成功前，不要把该版本发给同事或客户。

推送不动时先看这里（本机网络环境相关）：

- 报 `Empty reply from server` → 本机直连 GitHub 不通，临时挂代理即可，不改全局配置：

```bash
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push origin main
```

- 报 `could not read Username` / `terminal prompts disabled` → 凭据不在环境变量里，而在
  Git Credential Manager（GCM）中。`cmdkey /list` 查不到**不代表没有凭据**，用这个取：

```bash
"C:/Program Files/Git/mingw64/bin/git-credential-manager.exe" github list
printf 'protocol=https\nhost=github.com\n\n' | GIT_TERMINAL_PROMPT=0 \
  GCM_INTERACTIVE=never "C:/Program Files/Git/mingw64/bin/git-credential-manager.exe" get
```

- 不要走明文 `http://`（GitHub 301 强制跳 https）或 SSH（本机 `.ssh/` 没有 key）。
- 自动化 agent 的完整配方见技能 `github-push-behind-proxy`。
